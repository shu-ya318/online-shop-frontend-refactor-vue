# component(元件拆分判斷)

- 開發思路：先決定「要不要拆元件」,再刻畫面、最後接資料。

## 判斷流程

````text
畫面或邏輯想抽出來
│
▼
【0 警訊】檔案超過約 300 行?同時處理多件不相關的事?
│   (備註：用來提醒「去檢查第 1 步」,不一定要拆)
▼
【1 單一職責】自己依賴 store / router / 通知,
│            而父元件只靠 props / emit 運作?
├─ 是 ─► 抽成元件(為隔離依賴,只用一次也可以)─► 結束
│
▼ 否
【2 重複次數】在專案中重複幾次?
├─ 少於 3 次 ─► 先不抽,等第 3 次 ─► 結束
▼ 3 次以上
【3 差異】差異是「資料」還是「行為」?
├─ 行為不同(例如：成功後處理邏輯不同)
│     ─► 各寫各的;完全相同部分可另抽出純函式 ─► 結束
▼ 只有資料不同(文字、欄位、數量)，但行為邏輯相同
【4 呼叫端】抽出後,呼叫的地方一眼看得懂嗎?
├─ props 出現「開關某行為」的布林或 mode
│     ─► 多半抽錯,回到【3 差異】思考
▼ 看得懂
【5 形式】依「需要什麼、好不好測」決定形式
├─ 不需要 DOM 與響應式 ─────────────────► 純函式(最好測)
├─ 需要模板、DOM 或自己的狀態 ───────────► 元件
└─ 需要共用響應式狀態,或 UI 與資料處理 /
   API 請求強耦合 ──────────────────────► composable
│
▼
抽出
```        |

### 備註：沒放進流程的依據

- 「為了避免重複渲染而隔離狀態」:主要是 React 的考量(狀態更新會重渲染整個元件)。Vue 的響應式是細粒度追蹤,通常不是抽出的主要理由，所以不列為流程裡的判斷步驟。


## 決策表

### 適合抽出

| 候選                                 | 決定       | 理由                                                                                                                                                                                                                                              |
| ------------------------------------ | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AppHeader`、`AppSidebar`            | 抽成元件   | 桌機橫排、手機抽屜,呈現方式不同且各有互動(漢堡鈕、焦點管理);資料(`navItems`、開關狀態)由 `MainLayout` 往下傳                                                                                                                                      |
| `UserProfileMenu`                    | 抽成元件   | 流程第 1 步:只在 `AppHeader` 用一次,為隔離依賴而抽。它自己讀 auth / user store、route、router 並呼叫 `notify`(狀態 `isLoggingOut`、登出流程、登入 / 登出分支),`AppHeader` 因此只靠 props 與 emit(`navItems`、`sidebarOpen`、`toggle-sidebar`)運作 |
| `FormField`(label、必填、錯誤、aria) | 抽成元件   | 4 個頁面共 11 個欄位都用;差異只有資料(`name`、`label`、`required`、`hint`);`aria-*` 手寫容易錯,集中在一處                                                                                                                                         |
| `PasswordField`(顯示切換)            | 抽成元件   | 登入、註冊、重設密碼共 4 處;「顯示 / 隱藏」是它自己的狀態,放在頁面會變成多餘的狀態                                                                                                                                                                |
| `AuthForm`(表單外框)                 | 抽成元件   | 4 個頁面的容器、標題、錯誤提示、送出鈕結構一樣;`focusFirstError`、注音輸入保護需要 `<form>` 元素,只有擁有它的元件做得到                                                                                                                           |
| `splitApiError`(錯誤分流)            | 抽成純函式 | 4 頁的 `catch` 相同;放在 `utils/formErrors.ts`,有 `utils/__tests__/formErrors.spec.ts`;頁面只剩解構兩個值                                                                                                                                         |

### 不抽出

| 候選                                                              | 決定 | 理由                                                                                                                                                                         |
| ----------------------------------------------------------------- | ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `AppTextField`(把 `hide-details`、`:error`、`variant` 包起來)     | 不抽 | `variant`、`density` 已用 Vuetify 的 defaults 設定;剩下的 `hide-details`、`:error` 明寫在欄位上,看得出「錯誤由 `FormField` 顯示」;多包一層就多一份要轉接的 props、插槽與事件 |
| `AuthSubmitButton`                                                | 不抽 | 只在 `AuthForm` 裡用一次                                                                                                                                                     |
| `AuthLink`(連結樣式)                                              | 不抽 | 只有樣式相同,用 `AuthForm` 的 `:slotted(a)` 處理                                                                                                                             |
| `useAuthForm()`(`submitError`、錯誤分流、導頁包在一起)            | 不抽 | 4 頁成功後的處理不同,會長出切換行為的參數                                                                                                                                    |
| `applyApiError(form, error)`(一行完成 `setErrors` 並回傳整體錯誤) | 不抽 | 同時改狀態又回傳值,讀的人要點進去才知道做了什麼;拆成純函式加兩行明寫,比較好逐行解釋,也比較好測                                                                               |

### 暫時先不抽出

| 候選                                       | 決定   | 理由                                                                                                  |
| ------------------------------------------ | ------ | ----------------------------------------------------------------------------------------------------- |
| `focusFirstError`、注音保護抽成 composable | 先不抽 | 目前只有 `AuthForm` 一個使用者;之後設定頁的對話框成為第二、三個使用者時再抽                           |
| `BaseDialog`、`ConfirmDialog`              | 待確認 | `ConfirmDialog` 使用 `BaseDialog`,但 `src/` 目前沒有其他地方使用 `ConfirmDialog`;是否為預先抽出待確認 |
| `SearchInput`、`StagePlaceholder`          | 待確認 | `src/` 目前沒有任何 `.vue` 使用它們(僅以標籤搜尋確認,動態引用待確認)                                  |

## 應避免的錯誤

- 錯誤16:為了「統一」把 Vuetify 元件再包一層(例如 `AppTextField`)
  - 包裝層只是把 `v-text-field` 的 props 轉接出去
- 後果
  - 每多一個要用的 prop、插槽或事件,就要在包裝層補一份轉接;呼叫端也看不出哪些行為被預設了
- Vue 版做法
  - 全站一致的外觀用 Vuetify defaults(`plugins/vuetify.ts`);只有「元素之外還帶行為」(label、aria、錯誤)才包成元件,如 `FormField`

- 錯誤17:行為不同卻硬抽成一個 composable(例如 `useAuthForm`)
  - 4 頁的送出成功後處理不同
- 後果
  - 為了涵蓋差異,參數會長出「切換行為」的布林或 mode,呼叫端要查原始碼才知道實際行為
- Vue 版做法
  - 相同的部分抽純函式(`splitApiError`),不同的部分留在頁面明寫

- 錯誤18:函式同時改狀態又回傳值(例如 `applyApiError`)
  - 一行呼叫做了兩件事
- 後果
  - 讀的人必須點進函式才知道有副作用;也比較難單獨測試
- Vue 版做法
  - 純函式只負責計算並回傳(`splitApiError`),頁面再用兩行明寫 `setErrors` 與設定整體錯誤

## 新增元件時的檢查清單

1. 依「判斷流程」從【0】走到【5】,把結果補進上方對應的決策表(候選 / 決定 / 理由)。
2. 決定抽出後,先從假畫面抽 props / emits,再接資料。
3. 新元件需對應 spec,放在 `components/__tests__/`(`CLAUDE.md` 的測試規則)。
````

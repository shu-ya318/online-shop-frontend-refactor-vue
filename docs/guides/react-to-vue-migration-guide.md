# React 轉 Vue 重構指引

- 任何系統把 React 前端重構成 Vue 時可套用的原則。
- 只講方法與順序,不含特定專案的範例,也不套用 `docs/writing-guide.md`(該規範只管 `docs/setup/`)。

## 適用範圍與前提

### 適合轉換的情況

- 團隊已具備 Vue 能力,或後續維護者以 Vue 為主。
- 現有程式碼有明確的功能邊界(頁面、API 層、狀態)可以逐塊對應。

### 開始前先確認

- 現有功能可被驗證:有測試,或至少有一份功能清單可手動比對。
- 在獨立分支或獨立目錄作業,隨時能退回原版。
- 後端 API 不變;重構只動前端。

## 重構原則

- 功能不變:重構期間不新增功能,避免分不清問題出在轉換還是新功能。
- 先設定、後程式碼;先能跑、再補功能。
- 每一步都要驗收,通過才進入下一步。
- 與框架無關的程式碼先決定是否保留或移除，若要保留必須先測試，通過後原樣搬或調整。
- 重寫是「換成 Vue 的慣用做法」,不是逐行翻譯。

## 策略選擇

| 策略       | 做法                      | 適用條件                 |
| ---------- | ------------------------- | ------------------------ |
| 一次重寫   | 另起新專案,全部完成後切換 | 規模小、可停止新功能開發 |
| 漸進式遷移 | 新舊並存,逐頁或逐模組替換 | 規模大、系統需持續上線   |

- 選定後在文件記錄理由,中途不輕易改變。
- 漸進式遷移要先決定新舊如何共存(路由分流或獨立部署),並設定結束時間,避免兩套長期並存。

## 通用順序

| 階段 | 做什麼                                                 | 原因                        | 驗收                       |
| ---- | ------------------------------------------------------ | --------------------------- | -------------------------- |
| 1    | 盤點現有專案                                           | 先知道有什麼,才估得出工作量 | 產出功能、依賴、頁面清單   |
| 2    | 建置工具與套件管理                                     | 後面所有步驟都依賴能建置    | 安裝與啟動開發伺服器成功   |
| 3    | TypeScript 與路徑別名設定                              | 先固定型別規則              | 型別檢查通過               |
| 4    | 程式碼規範(lint、格式化、編輯器設定)                   | 規則先定,程式碼撰寫才一致   | lint 沒有錯誤              |
| 5    | 入口檔與根元件                                         | 先確認應用程式能掛載        | 開發伺服器顯示根元件       |
| 6    | 搬移與框架無關的程式碼(如：services, utils, constants) | 風險最低,可立刻跑測試       | 單元測試通過               |
| 7    | 路由                                                   | 頁面與權限控管的骨架        | 各路由可進入,守衛行為一致  |
| 8    | 全域狀態                                               | 頁面會依賴,需早於頁面       | 狀態讀寫與重置行為一致     |
| 9    | 多語系與 UI 元件庫                                     | 頁面共用的基礎              | 共用元件可正常顯示         |
| 10   | 共用元件與共用邏輯                                     | 頁面由這些組成              | 元件測試通過               |
| 11   | 頁面(由簡單到複雜)                                     | 前面都穩定後再逐頁轉換      | 每頁功能與原版一致         |
| 12   | 測試                                                   | 確認重構後行為與原版相同    | 單元與端對端測試通過       |
| 13   | 建置、容器化與部署                                     | 最後確認可上線              | 建置成功,部署後頁面可用    |
| 14   | Git hooks 與 CI                                        | 防止之後退回不一致狀態      | 故意提交有問題檔案會被擋住 |

- 順序是一般建議;但有依賴關係的項目不可前後對調(如：全域狀態早於頁面)。
- 每個階段完成就提交,commit 範圍保持單一。

## 概念對照方法

不背對照表,依下列層面逐項比對「原本怎麼做、Vue 慣用做法是什麼」:

- 元件狀態與衍生資料
- 副作用與生命週期
- 元件間資料傳遞與事件
- 全域狀態
- 路由與導覽守衛
- 表單與驗證
- 多語系
- UI 元件庫與樣式
- 資料請求與錯誤處理

做法:

1. 為每個層面,在原專案找出所有使用處。
2. 決定 Vue 端採用哪種寫法,並整個專案統一。
3. 把決定寫進專案的慣例文件,後續轉換照著做。

## 哪些可以直接搬

- HTTP 請求層與錯誤處理
- 純函式、工具函式
- 型別定義與資料驗證規則
- 常數與設定值
- 多語系的文案檔

搬移後只調整匯入路徑與型別,邏輯不改,並沿用原有測試驗證。

## 驗收清單

每個階段固定執行:

- [ ] 型別檢查通過
- [ ] lint 通過
- [ ] 單元測試通過
- [ ] 建置成功
- [ ] 與原版逐項比對功能

## 常見陷阱

- 逐行直譯:把原本的寫法硬翻成 Vue,結果得到不慣用、難維護的程式碼。
- 同時改功能:轉換中順手加新功能,出問題時無法判斷原因。
- 新舊依賴並存:兩邊框架的套件同時留著,造成版本衝突與打包體積變大。
- 忽略環境差異:環境變數、路徑別名、建置輸出在換工具後行為不同,沒有重新驗證。
- 沒有統一決定就開工:同一種需求在不同頁面用不同寫法,最後要二次整理。
- 文件沒有同步:程式結構改了,說明文件仍寫舊的檔名與流程。
- 遺漏非功能面:無障礙、SEO、錯誤頁、權限、效能,轉換時沒有逐項比對。

## 完成標準

- 原有功能清單全數通過比對。
- 不再有 React 相關依賴與程式碼殘留。
- 型別檢查、lint、測試、建置全數通過。
- 部署後的行為與原版一致。
- 專案文件已更新為 Vue 版現況。
